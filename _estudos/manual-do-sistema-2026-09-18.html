0. Como este manual foi feito — e o que “100%” significa aqui

Você pediu engenharia reversa de 100% do código. Antes de qualquer outra coisa, preciso dizer com precisão o que eu fiz — senão você confiaria em algo diferente do que está escrito aqui.

O que eu fiz, exatamente
  • Inventariei 100% dos arquivos. Percorri o repositório inteiro com um programa, contando arquivos e linhas, sem exceção — e todo número deste manual saiu dessa medição, feita hoje, não da minha memória.
  • Extraí do SQL, por programa, tudo o que o banco cria: cada tabela, cada função, cada policy, cada gatilho, cada permissão concedida. Nenhum desses números foi digitado por mim à mão.
  • Li em profundidade os arquivos que DECIDEM comportamento — os que controlam entrada, permissão, dinheiro, datas e as regras do módulo.
  • Rodei as provas e uso os resultados reais, não os esperados.
O que eu NÃO fiz — e você precisa saber
  • Não li as 68.255 linhas uma a uma. Ninguém lê — e quem disser que leu está inventando. Li a estrutura inteira e o miolo do que importa.
  • Não executei o sistema publicado para conferir a tela: eu não abro navegador. O que digo sobre telas vem do código delas.
  • Não testei o aplicativo de celular num aparelho. Ele nunca foi publicado em loja nenhuma, e há coisas nele que só um aparelho responderia.

Então “100%” aqui quer dizer: nenhuma parte do sistema ficou de fora do inventário, e nada neste documento é suposição. Onde eu não tiver certeza, está escrito que não tenho.

⚠️ Uma coisa que encontrei logo no começo, e que você precisa decidir

A pasta _estudos/ está vazia de estudos. Os 16 arquivos HTML que moravam lá — incluindo o manual anterior, a especificação do módulo e o estudo que entreguei há pouco — não estão mais no disco.

2. O que é este sistema, em linguagem comum

2.1 O Sol e as peças de LEGO

Imagine um prédio de escritórios. O prédio tem portaria, elevador, luz, água e a lista de quem pode entrar em cada andar. Nada disso é “o negócio” de ninguém — é a base. Cada empresa que aluga uma sala traz o próprio negócio para dentro.

No prédioNeste sistema
O prédio: portaria, elevador, chaves A PLATAFORMA — login, usuários, empresas, permissões, cores, perfil, auditoria. Funciona sozinha, sem nenhum módulo.
A sala de uma empresa, com os móveis dela UM MÓDULO — hoje existe um só: o Controle Financeiro. Ele se pluga e se despluga sem quebrar o prédio.
Por que essa separação é levada tão a sério aqui

Porque um dia você vai querer um segundo módulo — ou vai querer vender a plataforma sem o financeiro. Se o código dos dois estiver misturado, separar depois custa uma reescrita. Existe até um programa que confere isso a cada entrega (o npm run modulos:verificar): ele varre 295 arquivos e reclama se encontrar o nome de um módulo escrito num arquivo da plataforma.

2.2 As quatro palavras que você precisa saber

PalavraO que significa, sempre
PlataformaA base. O prédio. Funciona sem módulo nenhum.
MóduloUm pacote de funcionalidade de negócio. A peça de LEGO.
Ponto de solda Um dos três lugares (não mais que isso) onde o nome de um módulo pode aparecer na plataforma. Desplugar o módulo = desfazer três soldas.
Manifesto O cartão de visita que o módulo entrega à plataforma: id, nome, descrição, rota, prefixo de banco, versão. São 35 linhas e é o que torna o módulo “visível”.

A regra de ouro da segurança deste sistema, em uma frase

Quem decide o que cada pessoa pode fazer é o BANCO DE DADOS, nunca a tela. A tela esconde botões por educação — para não oferecer o que vai ser recusado. Mas se alguém contornar a tela, o banco recusa do mesmo jeito. É por isso que este sistema tem 68 provas rodando dentro do banco (seção 8).

A regra do “um arquivo, uma função” — e ela é real

O projeto proíbe arquivos que fazem muitas coisas: passou de ~150 linhas, deve ser fatiado. Dá para ver o efeito na medição: 312 arquivos para 68 mil linhas — média de 219 linhas por arquivo, e a média inclui o lockfile de 13.810 linhas.

Exemplo concreto: a tela “Meu Perfil” do site não é um arquivo — são cinco: a moldura, o estado, a leitura, a edição e a confirmação de exclusão. Cada um cabe na tela do editor inteiro.

4. A PLATAFORMA — a base que funciona sozinha

4.1 As 7 tabelas, e o que cada uma guarda

TabelaO que guardaSe ela sumisse…
users O perfil de cada pessoa: nome, e-mail, país, estado, cidade, se é o Desenvolvedor, se completou o cadastro. ninguém teria nome — o login existiria, a identidade não
tenants As empresas. Nome, apelido de URL (slug), quem é o dono, se está ativa. não haveria de quem são os dados
tenant_members O coração da permissão. Liga pessoa ⇄ empresa, com o papel (OWNER/DEPENDENT/VIEWER), a lista de módulos liberados e as permissões de cada módulo. todo mundo veria tudo, ou nada
global_settings Uma linha só (id = 1): as cores do sistema, o título e os e-mails de administração. o sistema perderia a identidade visual
audit_log A trilha de auditoria: o que mudou, em que tabela, quem fez, e o registro inteiro antes e depois. a lixeira do financeiro deixaria de existir — ela vive daqui
platform_modules O catálogo de módulos que existem no sistema. Nasce vazia: quem escreve a linha é o próprio módulo, ao ser instalado. a permissão negaria tudo, sem explicar por quê
tenant_modules O que cada empresa contratou. não haveria como vender um módulo a uma empresa e não a outra
A regra das DUAS CHAVES — a que mais confunde no começo

Para uma pessoa usar o Controle Financeiro, duas coisas precisam ser verdade ao mesmo tempo:

  1. a empresa dela contratou o módulo (linha em tenant_modules);
  2. o Proprietário liberou aquele módulo para ela (allowed_modules).

Faltando qualquer uma, o acesso é negado. E quem cruza as duas é uma função do banco (modulos_do_membro) — nunca a tela. Se um dia aparecer um “42501 Sem permissão” que não faz sentido, a primeira coisa a conferir é se a linha do módulo existe no catálogo.

A plataforma tem 27 funções dentro do banco. Sete delas são “gatilhos” — código que o banco dispara sozinho quando uma tabela muda — e por isso não recebem permissão de ninguém. As outras 20 são chamadas pelas telas.

As 12 policies são as regras de “quem enxerga qual linha”. Exemplos reais: “Ver os próprios vínculos”, “Dono atualiza a própria empresa”, “Desenvolvedor lê a trilha de auditoria”.

Por que toda policy deste projeto tem a palavra TO

No PostgreSQL, uma policy escrita sem a cláusula TO vale para PUBLIC — todo mundo, inclusive quem não fez login. Foi assim que a lista de usuários ficou aberta até a v9 deste projeto. Hoje existe uma prova automática que falha se alguém escrever uma policy sem TO.

Dependente botão do Google Mesmo caminho. Passou a ser assim em 13/09 porque antes ele não tinha como entrar de jeito nenhum: caía num formulário de senha, e para ter senha precisaria de um cadastro que o menu não oferece mais.

Os restos daquela época sobrevivem apenas como comentários explicando o erro, e eu confirmei hoje, por busca, que nenhum deles é código executável.

4.4 O proxy e o bloqueio de celular

O arquivo src/proxy.ts (104 linhas) roda antes de cada página do site e faz duas coisas: renova a sessão e barra celular no painel.

Três detalhes deste arquivo que valem por um curso
  1. Ele não pode falhar. Qualquer erro aqui derruba todas as páginas, inclusive a de login. Por isso ele tem dois escudos: se faltar configuração, ele registra e segue; se o Supabase cair, ele registra e segue.
  2. No Next.js 16 este arquivo mudou de nome. Chamava-se middleware.ts; virou proxy.ts, e passou a rodar sempre em Node.js (antes rodava no “Edge”).
  3. Ele NÃO autoriza ninguém. Está escrito no próprio arquivo: uma mudança de rota pode tirar o proxy do caminho sem ninguém perceber. Quem autoriza é o banco.

O bloqueio de celular tem duas camadas, e só uma vale de verdade:

CamadaComo funcionaVale?
proxy (por user agent) lê o “crachá” que o navegador apresenta e redireciona conveniência — crachá se falsifica em dois cliques
<MobileBlocker> (por largura) mede a largura real da janela: abaixo de 768px, cobre a tela é o portão de verdade

5. O CÉREBRO ÚNICO — o pacote @jairo/core

5.1 Por que ele existe

Há dois aplicativos neste projeto: o site e o aplicativo de celular. Os dois precisam saber as mesmas coisas — como entrar, o que é uma empresa, como formatar dinheiro, o que é uma data no Brasil. Se cada um soubesse por conta própria, um dia os dois discordariam — e ninguém perceberia até um cliente reclamar de um valor diferente em cada tela.

A regra, em uma frase

Toda inteligência de negócio nasce no Core. Os aplicativos só desenham tela e chamam o Core. Nenhuma validação, nenhuma chamada ao banco e nenhum cálculo moram dentro de uma tela.

Um detalhe técnico que explica muita coisa

O Core não é compilado. Ele é consumido como TypeScript cru pelos dois aplicativos — o site faz isso com uma linha no next.config.ts, o aplicativo com uma no metro.config.js. Por isso não existe (nem deve existir) um comando de “build do core”. Quem procurar um vai procurar para sempre.

5.3 As duas bibliotecas que evitam os erros clássicos

lib/dinheiro.ts — por que dinheiro aqui é número inteiro

Todo valor monetário neste sistema é guardado em centavos, como número inteiro. R$ 1.234,56 é o número 123456. Nunca 1234.56.

O motivo, com o exemplo que qualquer um pode reproduzir

Abra o console de qualquer navegador e digite 0.1 + 0.2. A resposta não é 0.3 — é 0.30000000000000004. Não é defeito do navegador: é como todo computador guarda número “com vírgula”.

Num extrato com mil lançamentos, esse resto aparece como um centavo que não fecha — e ninguém descobre de onde veio. Com centavos inteiros, 10 + 20 = 30, sempre. É a mesma razão pela qual o banco guarda esses valores como bigint.

lib/datas.ts — por que existe um arquivo inteiro para datas

São 398 linhas e 34 testes, e cada pedaço nasceu de um erro real:

O erro naturalO que aconteceO que o arquivo faz
toISOString() numa data 10/10 às 22h no Brasil vira 11/10, porque aquele formato fala em horário de Londres usa o calendário local
“mês anterior” com setMonth(-1) em 31/03 devolve 3 de março, sem erro nenhum — o botão “mês anterior” parece não funcionar ancora no dia 1 e pega o último dia pelo calendário
“30 dias atrás” com -30 × 86400000 supõe que todo dia tem 24 horas; no horário de verão há dias de 23 e de 25 diasAtras anda em dias de calendário

Note o padrão: nenhum desses erros quebra nada. Eles produzem uma resposta errada com cara de certa. É por isso que este arquivo tem mais testes que qualquer outro.

6. O MÓDULO FINANCEIRO — a peça de LEGO plugada

6.1 Os 3 pontos de solda (e por que são só 3)

Para o módulo existir aos olhos da plataforma, bastam três ligações. Eu as li hoje, uma a uma:

OndeO que está escrito lá
core/src/modules/registro.ts
duas linhas		 importa o manifesto do financeiro e o põe na lista MODULOS_INSTALADOS

Desplugar o Controle Financeiro é, portanto: desfazer essas três soldas, apagar as cinco pastas com o nome dele e rodar o reset do módulo no banco. A plataforma continua de pé.

6.2 As 5 tabelas do módulo

TabelaO que é, em linguagem comum
fin_contas_movimento Onde o dinheiro está. Caixa, banco, carteira. Tem saldo de abertura e é a única espécie de conta que “guarda” dinheiro.
fin_contas_identificadoras Por que o dinheiro andou. Aluguel, venda, salário. Ela explica, não guarda — e por isso não tem saldo: a coluna dela na conferência chama-se ACUMULADO.
fin_lancamentos Cada movimento: data, valor, entrada ou saída, de quem é (próprio/terceiros), regime (caixa/competência), ordem no extrato, se foi conferido.
fin_fechamentos Uma linha por conta dizendo “este período está trancado até tal dia”.
fin_orcamentos O plano do mês por conta identificadora. Nasceu ontem, e é a quinta tabela.
A distinção que organiza o módulo inteiro

Conta MOVIMENTO responde “onde”. Conta IDENTIFICADORA responde “por quê”.

Um aluguel pago pelo Banco Itaú é um lançamento que aponta para as duas: a conta movimento BANCO ITAÚ (de onde saiu) e a identificadora ALUGUEL (por que saiu). É isso que permite os dois dashboards: um soma por “onde”, o outro por “por quê”.

Uma regra de banco que parece exagero e não é (RN-29)

As ligações entre tabelas do módulo são duplas: carregam o id e a empresa. Com uma ligação simples, um lançamento da Empresa A poderia apontar para uma conta da Empresa B — e o banco aceitaria, calado. Existe uma prova automática só para isso, e uma linha de inventário que conta quantas ligações simples existem (tem de ser zero).

Três decisões dentro dessa lista que não são óbvias
  1. lc_excluir_lote é separada de lc_excluir_todos porque “apagar UM lançamento que não é seu” e “apagar UM ANO INTEIRO” são poderes de tamanhos diferentes. Com uma só, dar a primeira daria a segunda de brinde.
  2. Lançar pelo DINHEIRO DO PERÍODO continua exigindo lc_criar, a mesma de sempre. Uma permissão separada seria um segundo interruptor para o mesmo poder — e um dia os dois discordariam.
  3. O modo “só percentual” NÃO é permissão, de propósito: ela seria invertida (TER a permissão significaria VER MENOS), e um dia alguém marcaria a caixa achando que estava dando acesso. Ele mora num campo de configuração.
O que o modo “só percentual” esconde — e o que não esconde

Quando ligado, os valores não saem do banco: a função devolve orçado, realizado e saldo em branco, e só o percentual atravessa. Isso é real e tem prova automática.

Mas não é um cofre. Cinco outras permissões levam aos mesmos valores por outra tela: extrato_ver, lc_ver_todos, imprimir, orc_ver e cm_ver. A tela de configurações avisa dizendo quais, com um botão para retirá-las — avisar, e não bloquear, porque decidir isso pelo dono da empresa seria errado.

7. O APLICATIVO DE CELULAR — o que ele faz e o que não faz

A verdade sobre o aplicativo, sem rodeios

São 120 arquivos e 12.998 linhas — quase o tamanho do site. Ele tem login, perfil, painel do cliente, painel de engenharia com triagem de usuários, ajuste das cores do sistema, menus nativos, abas nativas, biometria e tema animado.

E ele não tem o Controle Financeiro. Nenhuma tela do módulo existe no aplicativo — o módulo é, hoje, exclusivo do site. Além disso, o aplicativo nunca foi publicado em loja nenhuma, e há um problema conhecido e adiado por você: o Dependente não consegue entrar pelo celular.

Você não roda nada na sua máquina: envia ao GitHub, a Vercel publica, e você testa no sistema. Isso significa que toda a conferência acontece antes — e é responsabilidade de quem escreve o código, não sua. Aqui está exatamente o que existe.

Por que as quatro camadas não se substituem — com o caso real

Em 18/09, um return morto citando uma variável que não existia passou pelo lint (ele não confere tipos) e passou pelos 98 testes (o Node só remove as anotações de tipo, não as verifica). Quem pegou foi o npm run build.

Cada camada enxerga uma coisa. Pular uma é escolher não ver aquela coisa.

O ensaio geral — um comando só

npm run ensaio roda as dez provas em sequência, inclusive subindo um banco PostgreSQL descartável, aplicando o SQL de verdade e rodando as travas. O resultado de hoje:

A décima prova é a mais importante, e é a menos óbvia

O ENSAIO DE UPGRADE monta um banco com o schema do commit anterior e aplica o de agora por cima — que é exatamente o que você faz no Supabase. Instalar num banco vazio não prova nada sobre um banco que já existe.

É aí que mora a armadilha mais cara deste projeto: mudar os parâmetros de uma função não substitui a função — cria uma segunda, e a antiga continua viva e alcançável. Já aconteceu três vezes.

A regra da mutação: toda trava tem de falhar uma vez

Uma prova que nunca falhou pode estar conferindo a coisa errada — e ninguém saberia, porque o resultado seria igualmente verde. Por isso, aqui, cada trava nova é vista falhar de propósito: quebra-se a função, roda-se a prova, e confere-se que a trava certa (e só ela) acusou.

⚠️ O que NENHUMA dessas provas cobre — e você precisa saber
  • O login de verdade. O banco descartável não tem o serviço de autenticação do Supabase. Google, senha, cookies e sessão só se provam no publicado.
  • A camada de tela. O banco tem 68 travas; o clique tem zero. O que dá para testar sem inventar dependências novas foi tirado das telas e levado para o Core — é por isso que existem arquivos de “regras” separados dos componentes. Clique, foco e rolagem continuam dependendo do seu dedo.
  • O aplicativo de celular. Zero testes automáticos, em 13 mil linhas.
  • As configurações do painel do Supabase (URLs de retorno, provedores, chaves) não estão no repositório e ninguém as confere daqui.

10. As sete travas de segurança do desenho

Estas sete decisões são o que protege os dados de uma empresa das outras — e de quem tentar contornar a tela. Estão listadas na ordem em que um curioso as encontraria.

TravaO que ela impede
1. RLS ligada em todas as tabelas Sem ela, qualquer pessoa logada leria a tabela inteira. Há uma linha de inventário que falha se alguma tabela do módulo ficar sem.
2. Toda policy com TO Policy sem TO vale para “todo mundo, inclusive sem login”.
3. REVOKE antes de GRANT No PostgreSQL, toda função nasce executável por PUBLIC. Só dar a permissão certa não fecha nada — é preciso tirar a de todos primeiro.
4. Permissão conferida DENTRO da função Esconder o botão não é segurança. Cada função pergunta ao banco quem está chamando.
5. SET search_path em toda função privilegiada Sem isso, quem chama pode “trocar o caminho” e fazer a função trabalhar sobre uma tabela falsa. Há uma prova automática para isso.
6. Chaves compostas entre tabelas do módulo Impede um registro de uma empresa apontar para o cadastro de outra.
7. Nada de chave-mestra na aplicação A chave que ignora toda a segurança não é lida por lugar nenhum do sistema — nem no site, nem no aplicativo.
O que continua sendo verdade, e não é confortável
  • Quem tem acesso ao painel do Supabase tem acesso a tudo. Nenhuma trava daqui vale contra a chave-mestra do projeto. Guarde-a como se guarda a chave do cofre.
  • Dado apagado de verdade não volta. A lixeira devolve lançamentos porque eles ficam guardados na trilha de auditoria. Apagar a trilha (o botão “LIMPAR TODA A LIXEIRA”) é o único ponto do sistema onde informação some para sempre — e a tela diz isso com todas as letras antes de confirmar.
  • Não há cópia de segurança configurada por este repositório. Backup é do Supabase, no painel dele. Se isso nunca foi conferido, vale conferir.

11. Receitas: como fazer as seis coisas mais comuns

1. Criar o banco do zero, num projeto Supabase novo

1) supabase/criar-bd/plataforma_01_schema.sql     (o 00_reset só se houver banco antigo)
2) supabase/criar-bd/plataforma_02_seed.sql
3) supabase/criar-bd-financeiro/financeiro_01_schema.sql
4) supabase/criar-bd-financeiro/financeiro_02_seed.sql

Cole um por vez no SQL Editor, limpando o editor (Ctrl+A) a cada arquivo.

2. Atualizar o banco depois de uma entrega minha

1) supabase/criar-bd-financeiro/financeiro_01_schema.sql   ← não apaga dados
2) supabase/testes/inventario_financeiro.sql               ← tem de dar 17 OK
3) supabase/testes/teste_financeiro.sql                    ← tem de dar 52 PASSOU

3. Conferir se o banco está íntegro (sem mudar nada)

Os dois arquivos de inventário só leem — pode rodar a qualquer momento, até em produção. Eles respondem OK ou DIVERGE linha a linha, e quando divergem nomeiam o objeto culpado.

4. Liberar o módulo para uma empresa

Desenvolvedor → /dashboard/modulos → escolher a empresa → ligar "Controle Financeiro"
Proprietário  → CONFIGURAÇÕES DO MÓDULO → marcar as permissões de cada integrante

Lembre das duas chaves: a empresa contrata, o Proprietário libera.

5. Recuperar um lançamento excluído por engano

CONFIGURAÇÕES DO MÓDULO → LIXEIRA → escolher a janela de tempo → RESTAURAR

Exige a permissão lc_excluir_lote. E o período não pode ter sido fechado depois da exclusão — nesse caso o banco recusa, de propósito.

6. Desplugar o módulo inteiro

1) supabase/criar-bd-financeiro/financeiro_00_reset.sql   ← ANTES do reset da plataforma
2) apagar as 5 pastas com o nome do módulo
3) desfazer os 3 pontos de solda
⚠️ A ordem aqui não é preferência

Rodar o reset da PLATAFORMA com o módulo ainda instalado destrói em silêncio as ligações das tabelas do módulo — as tabelas sobrevivem, quebradas, e reaplicar o schema não as conserta. O reset do módulo vem primeiro. Está escrito em supabase/LEIA-ME-ORDEM.md.
