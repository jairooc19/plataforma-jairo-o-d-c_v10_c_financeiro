2. Resumo em 12 frases

  1. O repositório é uma plataforma base (login, empresas, membros, cores do sistema) — sem nenhum módulo de negócio instalado. As telas operacionais mostram “Aguardando liberação”. VISTO NO CÓDIGO
  2. São três programas que compartilham um “cérebro”: o site (Next.js), o aplicativo (Expo/React Native) e o core (TypeScript comum), todos falando com um banco Supabase.
  3. Existem quatro formas de entrada: Proprietário (só Google), Dependente (e-mail e senha), Desenvolvedor (senha fixa no código) e Apenas Veja (só um aviso).
  4. O banco tem 4 tabelas, 9 funções, 12 regras de acesso (RLS) e 2 gatilhos, recriados do zero por três scripts SQL colados à mão.
  5. A documentação é extensa e cuidadosa, mas em vários pontos está desatualizada em relação ao código (versões, contagem de funções, arquivos citados que não existem).
  6. CRÍTICO As rotas de servidor que criam empresas, promovem usuários e mudam as cores do sistema não pedem identificação. Isso foi uma decisão consciente registrada no CLAUDE.md, mas para dados financeiros é inaceitável.
  7. ALTO Uma regra do banco deixa qualquer pessoa ler a lista inteira de usuários (nome, e-mail, cidade) usando a chave pública do app.
  8. ALTO Pelas regras atuais, qualquer pessoa com conta Google pode criar a própria empresa e pular a triagem do Desenvolvedor. DEDUÇÃO
  9. MÉDIO As datas de criação gravadas pelo banco ficam 3 horas atrasadas por causa de uma conversão de fuso feita duas vezes. DEDUÇÃO
  10. MÉDIO Operações de várias etapas (promover usuário, sincronizar empresas) são chamadas separadas, sem transação — o próprio CLAUDE.md proíbe isso.
  11. A estrutura de “módulos por membro” (allowed_modules) está pela metade: o banco guarda texto, o código espera lista.
  12. A pasta não é um repositório git e não há testes automatizados: hoje não há “botão de desfazer” nem rede de proteção para mudanças.

Por que “todas as colunas” e “criar” importam A documentação oficial do PostgreSQL diz que uma policy sem a cláusula TO vale para PUBLIC, isto é, todos os papéis. Diz também que, numa policy ALL ou UPDATE sem WITH CHECK, a expressão USING é usada também para aprovar as linhas novas. Na prática, “ser dono” vira permissão para inserir uma empresa em que você mesmo se declara dono. Fonte: [F1].

9. Fluxos passo a passo

9.1 Proprietário entra pelo Google — site

  1. Na guarita, escolhe “Usuário Proprietário” → LoginGoogleOwnerView.
  2. O popup do Google devolve um ID Token. O core troca por sessão com signInWithIdToken (googleAuthService.ts:67-77).
  3. O core chama ensure_google_user_profile para garantir o perfil.
  4. syncGoogleSessionAction copia a sessão para cookies do servidor (google-actions.ts).
  5. Portão: check_profile_completed. Se falta planeta, país, estado ou cidade → tela “Completar Cadastro”, sem botão voltar.
  6. Triagem: getUserTenants(id, 'OWNER'). Nenhuma empresa → “Aguardando Triagem”; uma → entra; várias → seletor.
  7. A empresa escolhida vai para sessionStorage.active_tenant_id e o navegador abre /dashboard.

9.2 Proprietário entra pelo Google — aplicativo

  1. useGoogleLogin pede ao Supabase a URL do Google com redirectTo = plataformajairo://auth/google.
  2. O navegador do sistema abre; o usuário escolhe a conta.
  3. Google → Supabase (callback do Supabase) → app (deep link com tokens no fragmento #).
  4. O retorno chega por dois caminhos: openAuthSessionAsync e a rota app/auth/google.tsx. Os dois usam oauthCallbackSession.ts, e a rota espera a sessão por até 6 segundos.
  5. A sessão é salva no aparelho (storageService.saveAuthSession). Seguem o mesmo portão e a mesma triagem da web.
Não funciona no Expo GoO Supabase rejeita o esquema exp://. É preciso development build. Isso está documentado e foi testado pelo dono do projeto em Android (apps/mobile-app/AGENTS.md). NÃO VERIFICÁVEL por mim.

9.3 Dependente entra com e-mail e senha

  1. Web: loginWithCatracaAction faz o login no servidor e grava os cookies. A “Catraca” é só decorativa (sempre libera).
  2. Mobile: authService.signIn direto e sessão salva no aparelho.
  3. Triagem com papel DEPENDENT. Sem vínculo → “Sem vínculos encontrados”.

9.4 Desenvolvedor

  1. developerSignIn compara duas strings (authService.ts:141-148). Não fala com o Supabase.
  2. Web: marca sessionStorage. Mobile: grava DEVELOPER no SecureStore.
  3. Ferramentas: Central de Comandos (triagem e empresas) e Ajustes Globais (cores). No mobile, elas chamam por HTTP as rotas do site, que usam a chave mestra.

9.6 Montar a equipe (Proprietário)

  1. “Gerenciar Equipe” → busca por e-mail (RPC get_user_by_email_for_invite).
  2. Liga ou desliga o crachá → upsert em tenant_members com papel DEPENDENT.
  3. Não há escolha de módulos: aparece “NENHUM MÓDULO CONTRATADO”.

9.8 Apagar a própria conta

delete_user_permanently compara o ID pedido com auth.uid() e recusa quem é dono de empresa. Na prática, só quem ainda não foi promovido consegue se apagar. Não existe função para transferir a propriedade de uma empresa.

9.9 Boot do aplicativo

  1. Carrega as fontes e as cores de global_settings.
  2. Verifica se o app abriu pelo deep link do Google.
  3. Restaura a sessão salva (AsyncStorage) e renova o token.
  4. Se o aparelho tem biometria cadastrada, pede digital ou rosto. Cancelar leva à guarita, sem deslogar.
  5. Com sessão vai para /(tabs); sem sessão, para /(auth). Começa a vigiar mudanças de permissão (Realtime).

13. Achados: segurança

Esta é a parte que mais pesa para um sistema financeiro. Os itens S4 e S5 são decisões conscientes já registradas no CLAUDE.md; mesmo assim eu os listo, porque o contexto muda quando entra dinheiro.

S1 · Qualquer pessoa lê a lista inteira de usuários ALTO VISTO NO CÓDIGO

Onde: plataforma_01_schema.sql:422-423 — CREATE POLICY "Acesso administrativo para triagem" ON public.users FOR SELECT USING (true);

Por que é problema: sem TO authenticated, a regra vale para todos, inclusive visitantes anônimos [F1][F9]. A chave pública não é segredo: o próprio .env.example do app avisa que ela é “embutida no bundle e visível no aparelho”, e o Next.js expõe ao navegador toda variável NEXT_PUBLIC_ [F7].

Na prática: alguém que extraia a chave do site consegue consultar direto a API do Supabase e receber e-mail, nome, estado e cidade de todos os usuários — sem login.

Contradição: a política de privacidade (privacidade/page.tsx:116) promete “mostrar apenas os dados das empresas às quais você tem vínculo”.

S2 · O usuário pode alterar o próprio role, is_superuser e is_client_owner MÉDIO DEDUÇÃO

Onde: plataforma_01_schema.sql:425-426 — UPDATE liberado quando auth.uid() = id, sem limitar colunas.

Na prática: um usuário logado pode gravar is_superuser = true na própria linha. A tela de Ajustes Globais usa exatamente essa coluna para liberar o acesso (dashboard/settings/page.tsx:68). Também pode se marcar active e aparecer como “Cliente Operacional” na Central de Comandos.

Caminho de correção conhecido: privilégios por coluna (revoke update … grant update (colunas)), documentados pelo Supabase [F10], ou gravar o perfil por uma função que só aceite os cinco campos editáveis.

S3 · Qualquer pessoa com conta Google pode criar a própria empresa e pular a triagem ALTO DEDUÇÃO

Onde: plataforma_01_schema.sql:446-447 (FOR ALL USING (auth.uid() = owner_id)) e 460-462 (dono insere membros).

Raciocínio, passo a passo:

  1. O login Google cria a conta automaticamente para qualquer pessoa (seção 9.1).
  2. Na regra FOR ALL sem WITH CHECK, o PostgreSQL usa o USING para aprovar linhas novas [F1]. Inserir uma empresa com owner_id igual ao próprio ID passa.
  3. Com a empresa criada, check_is_tenant_owner responde “sim”, e a regra “Donos podem inserir membros” aceita um vínculo OWNER para si mesmo.
  4. No login seguinte, getUserTenants(…, 'OWNER') encontra a empresa e a pessoa entra como Proprietário, sem passar pelo Desenvolvedor.

Não executei o teste num banco. A conclusão vem da leitura das regras e da documentação oficial do PostgreSQL.

S4 · Rotas de servidor com a chave mestra e sem identificação CRÍTICO VISTO NO CÓDIGO

Onde: as 9 rotas da seção 10.2 e as 3 Server Actions de dashboard/tenants/actions.ts. O próprio código registra isso (api/admin/users/route.ts:23-29, adminApiService.ts:26-30).

Na prática: quem souber o endereço do site pode, sem senha:

  • trocar título, cores e e-mails de alerta (POST /api/settings);
  • criar empresas para qualquer usuário (POST /api/users/promote);
  • desativar empresas de qualquer cliente (POST /api/admin/sync-tenants);
  • listar todos os usuários (GET /api/admin/users).

O que diz a documentação do Next.js: Server Actions são alcançáveis por POST direto, e é preciso “verificar autenticação e autorização dentro de cada uma” [F7].

Status: decisão consciente do dono do projeto em 07/09/2026 (CLAUDE.md). Minha recomendação é revê-la antes do C FINANCEIRO.

S5 · Desenvolvedor com senha fixa e “crachá” guardado no navegador ou no aparelho ALTO VISTO NO CÓDIGO

Onde: authService.ts:144; useAuthLogic.ts:182; dashboard/page.tsx:110; dashboard/tenants/page.tsx:57; usePasswordLogin.ts:40.

Na prática: a senha viaja dentro do JavaScript do site e do APK. Na web, basta criar dev_vip_access=true no sessionStorage para ver o console. Com S4, a tela nem é necessária: as rotas já estão abertas.

Status: risco conhecido e aceito (CLAUDE.md, 31/08/2026).

S6 · Funções com poder total, executáveis por qualquer papel MÉDIO DEDUÇÃO

Onde: get_user_by_email_for_invite (schema:256-264), sync_auth_users (268-293), ensure_google_user_profile (306-343).

  • No PostgreSQL, funções nascem com EXECUTE liberado para PUBLIC [F2]. O schema não revoga isso de nenhuma função.
  • Duas delas são SECURITY DEFINER sem search_path. O Supabase diz que, ao usar security definer, “você deve definir o search_path” [F3].
  • ensure_google_user_profile age sobre um ID recebido por parâmetro sem compará-lo com auth.uid(). O CLAUDE.md proíbe exatamente isso.

S7 · A sessão completa do mobile fica em armazenamento sem criptografia MÉDIO VISTO NO CÓDIGO

Onde: storageService.ts:128-138 — AsyncStorage.setItem('pjodc_supabase_session', JSON.stringify(session)).

Por que é problema: a documentação do React Native define o Async Storage como armazenamento “não criptografado” e diz para não usá-lo para tokens e segredos [F4]. O refresh token ali dentro permite gerar sessões novas.

Contexto honesto: o código explica a escolha (limite de tamanho do SecureStore). A documentação atual do Expo cita o limite de ~2048 bytes como histórico de algumas versões do iOS [F5]; o comentário do código fala em Android. Existe saída conhecida: criptografar o conteúdo e guardar só a chave no SecureStore.

Contradição: a política de privacidade diz que as credenciais ficam “no armazenamento protegido do sistema operacional” (privacidade/page.tsx:148-155).

S8 · Um único cliente Supabase compartilhado no servidor recebe o login do usuário MÉDIO DEDUÇÃO

Onde: auth/actions.ts:22 chama authService.signIn, que usa o cliente único de core/lib/supabase.ts:58-77 (criado uma vez por processo, com persistSession: true).

Por que é problema: num servidor que atende várias pessoas, esse cliente guarda em memória a sessão do último login. Qualquer consulta futura feita com ele no servidor roda “como” esse usuário. A documentação do Supabase manda criar um cliente novo a cada requisição no servidor, porque senão “o usuário ficará logado como a pessoa errada” [F8].

Hoje: o impacto é pequeno, porque o único uso do cliente público no servidor é ler as cores. Vira problema real no dia em que um módulo financeiro fizer leituras no servidor com ele.

14. Achados: funcionamento e integridade

C1 · Datas de criação gravadas 3 horas antes do horário real MÉDIO DEDUÇÃO

Onde: schema:61, 76, 86, 98 e plataforma_02_seed.sql:46 — DEFAULT timezone('utc', now() AT TIME ZONE 'America/Sao_Paulo').

A conta, passo a passo (documentação do PostgreSQL [F6])
  1. now() = 15:00 UTC, que é 12:00 em São Paulo.
  2. now() AT TIME ZONE 'America/Sao_Paulo' → um horário sem fuso: 12:00, “como apareceria naquele fuso”.
  3. timezone('utc', 12:00) equivale a 12:00 AT TIME ZONE 'utc': “assume que o valor está em UTC” → 12:00 UTC.
  4. Resultado gravado: 12:00 UTC. O certo seria 15:00 UTC. Diferença: −3 horas. Quem vê em horário de Brasília lê 09:00 para algo criado às 12:00.

Correção natural: DEFAULT now(). A coluna timestamptz já guarda o instante certo, e a conversão para Brasília acontece só na exibição. Confira antes de corrigir: rode select now(), created_at from public.users order by created_at desc limit 1; logo depois de criar um usuário.

C2 · Operações de várias etapas sem transação ALTO VISTO NO CÓDIGO

Onde: tenantService.ts:49-121 (syncUserTenants) e authService.ts:197-248 (promoteToOwner).

Exemplo de estrago: o Desenvolvedor cria três empresas de uma vez e a segunda tem nome repetido. A primeira já foi gravada, as desativadas já foram desativadas, e o role do usuário não foi atualizado. A tela mostra “nome duplicado”, mas o banco ficou pela metade.

Documentação que engana: api/users/promote/route.ts:17-19 diz “transação segura do Core”; adminApiService.ts:127 diz “É UMA OPERAÇÃO SÓ”. Isso vale só para a ida pela rede. Dentro do servidor são até 2 + 2n chamadas independentes.

Regra violada: “Nunca quebrar uma operação transacional do banco em chamadas TypeScript separadas — usar uma função SQL única” (CLAUDE.md).

19. Bônus: sugestões de alta relevância

B1 · Dinheiro nunca em número “quebrado” do computador

O PostgreSQL recomenda o tipo numeric para valores monetários e avisa que real e double precision são inexatos [F13]. No JavaScript acontece o mesmo. Testei no Node desta máquina:

0.1 + 0.2   → 0.30000000000000004
10.10 * 3   → 30.299999999999997
1010 * 3    → 3030   (centavos inteiros: exato)

Proposta: banco em numeric(14,2) ou centavos em bigint; no código, sempre centavos inteiros, formatando para R$ só na tela.

B2 · Dois tipos de data, cada um no seu lugar

Vencimento e competência são datas de calendário: tipo date, sem hora (evita o boleto que “vence ontem” por causa do fuso). Momento do registro é timestamptz DEFAULT now(). E corrigir o C1 antes, para não herdar o −3h.

B3 · Toda baixa financeira numa função SQL única

Exemplo: “pagar uma conta” = marcar o título como pago + lançar o movimento + atualizar o saldo. Ou acontece tudo, ou nada. É a regra que o CLAUDE.md já tem e que C2 mostra não estar sendo seguida.

B4 · Trilha de auditoria desde o primeiro dia

Uma tabela de histórico alimentada por gatilho: quem alterou, o quê, valor antigo, valor novo e quando. Em finanças, “quem mudou este valor?” é pergunta certa de acontecer.

B5 · Toda tabela financeira com tenant_id e RLS com TO authenticated

Reaproveitar check_is_tenant_member, nomear o papel em toda policy (recomendação oficial do Supabase [F9]) e revogar EXECUTE de PUBLIC nas funções [F2][F3].

B6 · Importação de extratos sem duplicar

Se houver importação de extrato bancário (OFX/CSV), guardar uma “impressão digital” de cada linha e recusar repetidas. Importar duas vezes o mesmo arquivo não pode dobrar o saldo.

B7 · Migrations de verdade antes de ter dados reais

“Derruba tudo e recria” é ótimo sem clientes. Com lançamentos financeiros reais, um reset apaga o histórico. O CLAUDE.md já prevê supabase/migrations/; o momento de adotar é antes do primeiro dado real.

B8 · Testes onde o erro custa caro

Não há nenhum teste hoje. Os primeiros deveriam cobrir: cálculos de dinheiro, regras de acesso entre empresas (a empresa A nunca vê dados da B) e funções transacionais.

B9 · LGPD

Dados financeiros ligados a pessoas são dados pessoais. A Lei 13.709/2018 [F14] exige, entre outros pontos, tratar só o necessário e adotar medidas de segurança. S1 e a política de privacidade atual precisam estar alinhadas antes de guardar dados financeiros. Esta é uma orientação técnica, não parecer jurídico.

B10 · Migrar middleware.ts para proxy.ts com cuidado

O Next.js oferece um codemod automático [F12]. Atenção: pela documentação, o proxy roda só no runtime Node.js; quem precisa do Edge continua em middleware. É preciso decidir isso de propósito, não por acidente.
