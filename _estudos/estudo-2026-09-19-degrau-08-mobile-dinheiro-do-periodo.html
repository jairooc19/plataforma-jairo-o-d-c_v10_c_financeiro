2.1 As sete palavras que você precisa ter em mãos

PalavraO que é, em linguagem comumA analogia
React Native A tecnologia que permite escrever a tela em TypeScript e o telefone desenhar com os componentes nativos dele. Não é um site dentro de um app: é app de verdade. O mesmo desenho, executado pelo pintor do Android e pelo pintor do iOS.
Expo Um conjunto de ferramentas em volta do React Native. Ele resolve o que ninguém quer resolver à mão: compilar, assinar, biometria, cofre, câmera, deep link. Aqui usamos o SDK 57. A caixa de ferramentas. Você poderia trabalhar sem ela, martelando cada parafuso.
expo.dev O site/painel da Expo na internet. É lá que ficam: o seu projeto, o histórico de compilações, os arquivos .apk prontos e as variáveis de ambiente. É o equivalente do que a Vercel é para o site. A Vercel do aplicativo.
EAS “Expo Application Services”. É o nome do serviço que roda na nuvem da Expo e compila o seu app. O comando que fala com ele é o eas. Compilar um Android sem EAS exigiria Android Studio e ~10 GB na sua máquina. A fábrica. Você manda o projeto; ela devolve o aplicativo instalável.
Metro Um servidor que roda na sua máquina e serve o código JavaScript/TypeScript ao aplicativo ao vivo. Você salva o arquivo, o telefone recarrega em 1 segundo. É o que npx expo start liga. O npm run web do aplicativo.
Expo Go Um app pronto, baixado da Play Store, que hospeda projetos Expo sem compilar nada. Ótimo para começar — e inútil aqui, pelo motivo da caixa abaixo. Uma casa alugada e mobiliada. Serve para dormir, não para instalar a sua porta.
development build O seu aplicativo, compilado pela EAS, com a sua identidade (com.jairo.plataforma) e o seu esquema de link (plataformajairo://), mas em modo de desenvolvimento: ele se conecta ao Metro da sua máquina. A sua casa, ainda com andaimes. É a sua porta, a sua fechadura.

O Proprietário deste sistema entra só pelo Google. Não existe configuração que resolva.

Este é o pedaço que mais confunde, e não é culpa sua: são quatro painéis diferentes, na internet, e cada um guarda uma coisa distinta. Quando algo não funciona, o erro quase sempre aparece no painel errado.

Pergunte sempre: “quem faz esta chamada?” O Google só conhece o Supabase, porque é o Supabase que fala com ele. O seu plataformajairo:// é assunto entre você e o Supabase. Cadastrar plataformajairo:// no Google é cadastrar um valor que o Google nunca vai comparar com nada.

2.5 O implícito: Wi-Fi, firewall, e por que o telefone “não acha” o PC

Num development build, o telefone precisa alcançar o Metro pela rede. Isso gera três tropeços que não têm nada a ver com o seu código:

SintomaCausa realO que fazer
O app abre e diz que não consegue conectar ao servidor de desenvolvimento Telefone e PC em redes diferentes (ex.: o telefone no 4G, o PC no Wi-Fi) Pôr os dois no mesmo Wi-Fi. Se a rede for “de visitante”, ela isola os aparelhos: trocar de rede.
Mesma rede e ainda assim não conecta O Firewall do Windows está bloqueando a porta 8081 Na primeira execução, o Windows pergunta se permite o Node: responda permitir em redes privadas. Se você já negou antes, é preciso liberar nas regras do Firewall.
Nada resolve, ou você está fora de casa — npx expo start --tunnel: o tráfego passa pela internet em vez da rede local. É mais lento e pede um pacote extra na primeira vez.
Erro estranho de módulo que “não existe”, depois de mexer em arquivos Cache do Metro npx expo start --clear. É o primeiro remédio, sempre.

Item 2 — o aplicativo lê a lista de módulos do lugar errado

Este é um defeito real, que eu encontrei hoje lendo o código, e ele mataria o degrau 08 em silêncio. Vou explicar do começo, porque é a lição mais importante deste estudo.

Para alguém abrir um módulo, o sistema exige duas chaves:

  1. a empresa contratou o módulo (tabela tenant_modules);
  2. o integrante foi liberado para ele (coluna allowed_modules, em tenant_members).

Quem cruza as duas é uma função do banco, a modulos_do_membro(). E ela tem uma regra especial, que é o coração do problema — LIDO em supabase/criar-bd/plataforma_01_schema.sql, linha 1189: 

CASE
  WHEN tmem.role = 'OWNER' THEN   -- o PROPRIETÁRIO recebe tudo o que a EMPRESA contratou
    (SELECT array_agg(tmod.module_id) FROM tenant_modules tmod ...)
  ELSE                            -- os demais recebem só o que foi marcado para eles
    COALESCE(tmem.allowed_modules, '{}'::text[])
END
O defeito, em uma frase

A coluna allowed_modules é a chave que o Proprietário entrega à equipe dele — para ele mesmo, ela normalmente está vazia. E o aplicativo lê exatamente ela: 

// apps/mobile-app/src/components/client/ClientDashboard.tsx, linha 70
const modulos = tenantData?.allowed_modules ?? [];
...
{modulos.length === 0 ? ( ... "Nenhum módulo ativo" ... )}

Resultado se nada mudar: você entra no aplicativo como Proprietário, com a empresa tendo contratado o Controle Financeiro, e o aplicativo diz “Nenhum módulo ativo — Aguardando habilitação de recursos pelo Desenvolvedor.” Nenhum erro, nenhum log, nenhuma pista. Só uma tela mentindo com muita elegância.

A correção — e ela já existe pronta no Core

O site já faz certo: ele chama moduleService.modulosPermitidos(tenantId), que é a função do banco. É uma linha: 

// em vez de ler allowed_modules:
const permitidos = await moduleService.modulosPermitidos(tenantId);  // → modulos_do_membro()
const modulos    = modulosDoMembro(permitidos);                      // → os manifestos

Curiosidade honesta: o próprio CLAUDE.md deste projeto já tem a proibição escrita — “Nunca exigir allowed_modules do PROPRIETÁRIO” — e o OperationalDashboardView do site tem um comentário dizendo “o aplicativo já fazia certo desde a v10: ele lia allowed_modules”. Esse comentário está errado: ler allowed_modules era o certo quando não havia módulo nenhum e ninguém notou a diferença. Isso também vai ser corrigido.

4. O que é o DINHEIRO DO PERÍODO — recapitulação para a tela pequena

Você conhece esta tela no site. Recapitulo por dois motivos: para eu deixar registrado exatamente o que vai ser portado, e porque um telefone não é um monitor — algumas coisas terão de mudar de forma, e você precisa concordar com quais.

4.1 A pergunta que a tela responde

Uma pergunta só: “do que eu planejei gastar/receber neste mês, quanto já aconteceu?” Ela compara o orçado (o plano, digitado na tela ORÇAMENTO) com o realizado (os lançamentos que existem de fato), conta por conta.

Os blocos aparecem sempre nesta ordem, e a ordem vem do banco, não da tela:

BlocoO que é
RECEITAO que se planejou receber. Aqui bater 100% é bom.
DESPESAO que se planejou gastar. Aqui bater 100% é o limite.
RESULTADOReceitas planejadas menos despesas planejadas, contra o que de fato aconteceu. É uma linha só.
OUTRASAporte e transferência. Não entram no resultado: não são resultado do negócio.
FORAContas que tiveram movimento e não estavam no orçamento. Não entram nos totais.

4.2 A barra, a cor e a marca do ritmo do mês

O pedido original era: “de modo que o usuário só no olhar saberá que do valor orçado já foi consumido X”. A barra é isso — a cor responde antes de a pessoa ler qualquer número.

Exemplo prático — como se lê uma linha

COMBUSTÍVEL  ·  ORÇADO 1.200,00  ·  REALIZADO 948,00

79%  —  sobram 252,00

A marca do ritmo é um risquinho vertical na barra, na posição de quanto do mês já passou. Consumir 79% no dia 18 (60% do mês) é um recado; consumir 79% no dia 30 é outro completamente diferente. A barra sozinha não conta isso — a marca conta.

A regra que erra em silêncio, e que já está resolvida no Core

Nas RECEITAS o sentido se inverte. Numa despesa, 105% é vermelho (estourou). Numa receita, 105% é verde (superou a meta). Pintar de vermelho uma meta cumprida seria dizer o contrário do que aconteceu.

Quem decide cor, largura e a frase ao lado é orcamentoRegras.ts, no Core, com teste. MEDIDO: o arquivo tem 184 linhas, importa somente um tipo e nada de runtime — ou seja, funciona igual no telefone, sem nenhuma adaptação. O aplicativo vai usar as mesmas quatro funções que o site usa: faixaDeConsumo, larguraDaBarra, situacaoDaLinha e agruparEmBlocos.

4.3 O modo “só percentual”, e por que ele é decidido no BANCO

Este é o muro que a quarta rodada de 18/09 derrubou, e eu preciso que ele fique claro antes de escrever a tela do telefone, porque a tentação de repetir o erro é enorme.

O caminho errado — e por que ele NÃO esconde nada

O jeito natural seria: o banco manda tudo, e a tela decide não mostrar os valores. Isso não esconde nada. Os números atravessam a internet e ficam legíveis no aparelho. Não é preciso saber programar — basta saber onde olhar.

Esconder numa tela é conforto. Não enviar é segurança.

O caminho certo, já construído — LIDO no schema, linha 3295

A função fin_dinheiro_do_periodo lê o modo daquele integrante e, no modo percentual, devolve orcado_centavos, realizado_centavos e saldo_centavos em NULO. Só o percentual sai do banco.

Consequência para o aplicativo: a tela do telefone não vai ter nenhuma linha escondendo valor. Ela só vai perguntar “o valor veio nulo?” e, se veio, escrever “VALORES OCULTOS — VOCÊ VÊ SOMENTE O PERCENTUAL”. A decisão não é dela. Se um dia alguém escrever um if de esconder valor na tela do telefone, isso é um defeito, e este parágrafo é a prova de que era sabido.

4.4 O bloco FORA — o gasto que ninguém planejou

Uma conta em que se gastou e não se orçou some de qualquer relatório de orçamento — e é justamente o gasto imprevisto que se precisa ver. O bloco FORA existe para isso, com fundo diferente, uma frase explicando, e fora dos totais.

Detalhe que a tela do telefone tem de respeitar

“Não ter orçamento” é diferente de “ter só o bloco FORA”. Se o FORA contasse como orçamento, a tela mostraria só o gasto imprevisto e diria que o mês está orçado — o oposto da verdade. A regra já está no site (useDinheiroDoPeriodo.ts) e vai junto: 

const semOrcamento = !carregando && !linhas.some(
  (l) => l.linha_tipo === "CONTA" && l.bloco !== "FORA",
);

B Deduzir: “a rota é / + o id do módulo”. Mágica implícita. E pior: não há como um módulo dizer “eu não tenho tela no telefone” — o painel ofereceria um cartão que leva a um endereço inexistente, e o usuário cairia no “Endereço não encontrado”.

Aqui a rota existe; o que o TypeScript não sabe é que a string é ela. São coisas diferentes. Proposta: um ponto de conversão, num arquivo só, com o comentário explicando exatamente isto. Se você preferir evitar o cast por completo, a alternativa é o cartão receber a função de navegação já pronta, e aí não há string atravessando fronteira — é mais código para o mesmo efeito. Três decisões pequenas que valem estar escritas

1. O rótulo anuncia o DESTINO do toque, não o estado. Um botão escrito "SÓ %" enquanto o ecrã mostra valores é ambíguo: metade das pessoas lê "estou em SÓ %" e a outra metade lê "toque para ir a SÓ %". O estado atual já está à vista — são os próprios números.

2. A preferência vai ao cofre do aparelho, não a estado de tela. Sair da tela e voltar remonta o componente: quem tivesse escondido os valores para mostrar o ecrã a alguém os veria reaparecer sozinhos. 3. No modo "SÓ %", a frase da linha muda de redação em vez de desaparecer. A situacaoDaLinha do Core já escrevia diferente quando o saldo é nulo: em vez de "SOBRAM 252,00" ela escreve "79% CONSUMIDO" / "ESTOUROU (112%)". Esconder a frase inteira teria sido mais fácil e tiraria o aviso de estouro, que é a informação mais útil da linha.
