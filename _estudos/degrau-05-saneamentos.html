4. O soquete: manifesto e registro

FEITO E VALIDADO São dois arquivos pequenos no Core, e eles são a razão de tudo o mais funcionar.

4.1 packages/core/src/modules/tipos.ts — o formato do pino

Declara o ManifestoDeModulo: id, nome, descrição, rota, prefixo de banco, versão e a versão mínima de plataforma exigida. É a única coisa que a plataforma sabe sobre um módulo.

A regra escrita dentro do próprio arquivo

"Nunca acrescente a este tipo um campo que só um módulo usa." No dia em que ManifestoDeModulo ganhar taxaDeJuros?: number, a plataforma terá passado a conhecer o negócio de uma das peças — e a peça seguinte carregará um campo sem sentido para ela.

4.2 packages/core/src/modules/registro.ts — ⚡ o ponto de solda nº 1

Hoje ele está assim, e isto não é um esboço: é o estado correto de uma plataforma sem módulos.

export const MODULOS_INSTALADOS: ManifestoDeModulo[] = [
  // (nenhum módulo conectado — ver `MODULOS.md`)
];

export function modulosDoMembro(permitidos) { ... }   // cruza ids com manifestos
export function manifestoDoModulo(id) { ... }         // acha um manifesto pelo id
Uma decisão de projeto que vale explicar: o id órfão é ignorado em silêncio

Se um módulo for desplugado do código mas ainda houver membros com ele em allowed_modules, o menu simplesmente não desenha o cartão — em vez de quebrar a tela do cliente com um destino que não existe mais. A limpeza dessas sobras é responsabilidade do reset do módulo (regra B5 do degrau 4, agora escrita no mapa).

É o mesmo princípio do settingsService, que devolve a paleta de fábrica quando o banco não responde: a tela do cliente não é o lugar de denunciar inconsistência interna.

5. O catálogo no banco (lacuna L1)

FEITO, FALTA RODAR NO BANCO A tabela platform_modules resolve o "módulo fantasma".

Antes allowed_modules aceitava qualquer texto. Digitar 'financiero' gravava sem reclamar; o membro "tinha" um módulo que nunca abriria, e nada no sistema sabia dizer por quê.
Agora Todo módulo existe como linha em platform_modules, com o id validado pelo próprio banco (^[a-z][a-z0-9_]{2,29}$). O que não está no catálogo é recusado na hora.

5.1 Quem escreve no catálogo — e por que não é a aplicação

Quem grava a linha é o <nome>_02_seed.sql do próprio módulo, colado no SQL Editor junto com o banco dele. Não existe — de propósito — nenhuma função que cadastre módulo pela tela.

O motivo, em uma frase

Se a aplicação pudesse cadastrar módulos, existiria um módulo no catálogo sem tabelas, sem telas e sem manifesto — um nome apontando para o vazio, contratável por empresas, liberável a membros, e que só falharia na hora de abrir. O catálogo é consequência da existência do módulo, nunca a causa.

6. As duas chaves: contratar × liberar (lacuna L4)

FEITO, FALTA RODAR NO BANCO Esta é a mudança de comportamento mais relevante do degrau.

ChaveOnde moraQuem concedePor qual tela
A empresa contratoutenant_modules NOVADesenvolvedorPainel de Engenharia › Módulos (tela nova)
O membro foi liberadotenant_members.allowed_modulesProprietárioCentral de Comando de Tripulação

6.1 O buraco concreto que isso fecha

O Proprietário monta a própria equipe — o privilégio do banco dá a ele INSERT e UPDATE em tenant_members, limitados pela RLS à empresa dele. Consequência: ele podia escrever allowed_modules = {'financeiro'} para si mesmo, sem que a empresa jamais tivesse contratado o produto. Enquanto não há módulo, isso não tem efeito; no dia em que houver, é acesso a produto sem contratação.

6.2 A trava é um gatilho, e isso foi escolha

-- 7.6 no plataforma_01_schema.sql
CREATE TRIGGER validar_modulos_membro
  BEFORE INSERT OR UPDATE OF allowed_modules ON public.tenant_members
  FOR EACH ROW EXECUTE PROCEDURE public.validar_modulos_do_membro();
Por que gatilho e não policy

Uma policy sabe dizer "pode" ou "não pode" para a linha inteira. Aqui é preciso olhar cada item de um array e dizer qual deles é o problema. O gatilho consegue nomear o módulo recusado na mensagem de erro — e uma mensagem que nomeia o culpado é a diferença entre um minuto e uma tarde de depuração.

6.3 Descontratar limpa os membros — na mesma transação

A função admin_set_tenant_module(tenant, modulo, ativo), ao desligar um contrato, também remove aquele módulo do allowed_modules de todos os membros da empresa.

Por que isso não podia ficar para uma segunda chamada

Se o contrato fosse desligado e a limpeza não acontecesse, os vínculos ficariam com um módulo que a empresa não tem mais — e aí o próximo UPDATE em tenant_members (mudar o papel de alguém, desativar um colaborador) seria recusado pelo gatilho por causa de um resto que ninguém pediu. O Proprietário veria um erro incompreensível ao mexer em outra coisa. É exatamente a proibição do CLAUDE.md: operação multi-passo é uma função no banco.

Repare no que este arquivo NÃO tem

O nome de nenhum módulo. Ele recebe identificadores do banco, pede os manifestos ao registro e desenha um cartão para cada um. Plugar o décimo módulo não vai exigir tocar nesta tela — é isso que distingue um encaixe de uma lista de if.

7.1 A conta é feita no banco, não na tela

O painel chama moduleService.modulosPermitidos(tenantId), que chama a função modulos_do_membro(). É ela que cruza as três condições: liberado ao membro, contratado pela empresa e ativo no catálogo.

A tela poderia cruzar isso sozinha — e seria mais rápido de escrever. Mas então a regra viveria no navegador, onde se edita com o console aberto. É a lição do degrau 3 aplicada de novo.

7.2 A tela nova do Painel de Engenharia

/dashboard/modulos: lista as empresas à esquerda, o catálogo à direita, com um botão por módulo. Descontratar pede confirmação e avisa, no texto da confirmação, que os membros também perderão o acesso — porque é isso que vai acontecer.

Com zero módulos (hoje), ela mostra um aviso âmbar explicando que o registro do Core está vazio e o que fazer. Tela vazia sem explicação é defeito; tela vazia que ensina o próximo passo é documentação.

Duas decisões que fazem a diferença entre uma ferramenta usada e uma ignorada

1. Comentário não é solda. O lib/dinheiro.ts diz, num TSDoc, que foi escrito para o C FINANCEIRO. Isso não quebra nada quando o módulo sai — e reclamar disso treinaria você a ignorar o verificador.

2. E-mail de exemplo não é módulo. Na primeira versão, o módulo de teste chamado exemplo casou dentro de voce@exemplo.com, em dois arquivos do mobile e três linhas do teste SQL: cinco falsos positivos. Agora ocorrências dentro de e-mail e de domínio são descartadas. Verificador que grita à toa é desligado na terceira vez — e verificador desligado não protege nada.

9. O mapa MODULOS.md (lacuna L5)

FEITO E VALIDADO Na raiz, ao lado do CLAUDE.md, com dez blocos: o que é plataforma, os módulos conectados, os pontos de solda, as 10 regras, a anatomia de um módulo, os roteiros de conectar e desconectar, o histórico dos que já saíram, as duas chaves de acesso e o verificador.

O detalhe que faz o mapa não envelhecer

A plataforma é definida por exclusão ("tudo o que não está no bloco 2") e os módulos por enumeração. Se fosse o contrário, bastaria uma pasta nova na plataforma para o mapa passar a mentir. Do jeito que está, ele se mantém verdadeiro sozinho — e a lista que precisa de manutenção é a curta, que muda uma vez por módulo.

O CLAUDE.md e o README.md apontam para ele. Isso importa por um motivo prático: o CLAUDE.md é o arquivo que eu leio no começo de toda sessão — com o ponteiro lá, as regras do LEGO passam a valer para mim em todo degrau futuro, sem você precisar repeti-las.

13. ⚠️ O que VOCÊ precisa fazer agora

O banco precisa ser recriado

Há duas tabelas novas, seis funções novas, dois triggers novos e um gatilho novo. O banco que está no ar não os tem — e enquanto não os tiver, a tela /dashboard/modulos vai dar erro de função inexistente, e o painel do cliente vai listar zero módulos (o que, hoje, é o correto de qualquer forma).

  2. Recriar o usuário do Desenvolvedor: Authentication › Users › Add user (com Auto Confirm) e depois o UPDATE … SET is_superuser = true que está no fim do seed.
  3. Conferir a contagem: 7 tabelas, 25 funções, 12 policies, 15 triggers.
  4. Rodar supabase/testes/teste_rls.sql — agora são 14 linhas, todas devem dizer PASSOU. Os testes 10 a 13 são novos e cobrem exatamente a contratação de módulo.
  5. Entrar pelo Google e pedir a promoção como de costume (o reset apaga os usuários; você nasce pending de novo).
  6. Abrir o Painel de Engenharia › Módulos: a tela deve listar as empresas e mostrar o aviso âmbar de "nenhum módulo instalado no código". Esse é o comportamento correto de hoje.
  7. Enviar o commit (git push) para a Vercel construir a versão com a tela nova — e conferir no painel dela qual commit foi construído.
Se algum dos 14 testes falhar

17. Bônus novo: sugestões desta rodada

Coisas que surgiram enquanto eu implementava, não estavam no degrau 4, e que eu recomendo.

N1 — Rodar o verificador automaticamente antes de cada commit

Hoje ele é manual. Um hook de pre-commit do git (ou uma linha no npm run verificar, que já existe) faria a checagem acontecer sem ninguém lembrar. A regra que depende de memória humana é a regra que falha. Custa cinco minutos.

N2 — Um segundo módulo de mentira, permanente, só para teste

Hoje a única prova de que o encaixe funciona fim a fim é o raciocínio. Um módulo mínimo (exemplo, com uma tabela e uma tela de "olá") plugado e desplugado uma vez, antes do financeiro, exercitaria o caminho inteiro — e qualquer surpresa apareceria num módulo descartável, não no que guarda dinheiro.

N3 — O TeamManagementModal precisa tratar o erro do gatilho

Quando o Proprietário tentar liberar um módulo não contratado, o banco devolverá a mensagem "Módulo(s) não contratado(s) por esta empresa: X". Hoje aquela tela mostraria isso como erro genérico. Vale exibir a mensagem do banco tal como ela vem — ela já foi escrita para ser lida por gente.

N4 — Guardar o número de versão da plataforma no banco

O manifesto declara exigePlataforma: 'v10', mas hoje nada compara isso com a plataforma real em execução. Uma linha em global_settings com a versão do schema permitiria ao registro avisar: "este módulo exige v11, esta plataforma é v10". Só vale a pena quando existir o segundo módulo — anoto para não se perder.

N5 — Documentar o que acontece com dados do módulo ao desplugar

O roteiro atual apaga as tabelas do módulo. Isso apaga os dados dos clientes daquele módulo. Para o financeiro, é uma decisão séria: talvez o reset deva ter dois modos — "desplugar guardando os dados" (só tira o código e o catálogo) e "desplugar apagando tudo". Vale decidir antes de existir o primeiro registro financeiro, não depois.
